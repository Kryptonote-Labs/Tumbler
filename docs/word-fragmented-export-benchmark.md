# Fragmented paragraph export

The audit reproduction creates one paragraph with 8,000, 16,000 or 32,000 separate
`x` runs, imports it, then calls `reconcileWordContent`. The old `finishSource`
searched the original paragraph after every emitted run. Source-occurrence
accounting now counts remaining occurrences by source paragraph within each copy
scope. Duplicate occurrences each contribute to the count. Finalization scans the
source paragraph once per scope and retains the existing before/trailing markup
placement.

This changes bookkeeping, with no intended XML or public API change. It does not
establish general Word interoperability or security.

## Method

Use `scripts/benchmark-word-fragmented-export.ts` unchanged on both revisions.
Each size runs in a fresh Bun process, with one full warmup and three measured
samples. Fixture creation/import, GC and correctness checks are outside the timed
reconciliation. The script records wall time, process CPU time, heap delta,
process peak RSS, output XML bytes and SHA-256. Heap delta is a net measurement,
not total allocated bytes; peak RSS covers the whole process including fixture
creation and verification. Neither is a per-operation allocation profile.

```sh
git worktree add --detach /tmp/word-fragmented-baseline 4d1465ddf85ee238a727dbed75aac7bf043f05f8
cp scripts/benchmark-word-fragmented-export.ts /tmp/word-fragmented-baseline/scripts/
(cd /tmp/word-fragmented-baseline && bun install --frozen-lockfile)

# Run baseline, then fixed checkout, holding one lock across both.
flock -x /tmp/tumbler-word-audit-heavy.lock timeout 10m bash -c '
  for checkout in "$1" "$2"; do
    cd "$checkout"
    for n in 8000 16000 32000; do
      bun scripts/benchmark-word-fragmented-export.ts "$n" 3 1
    done
  done
' _ /tmp/word-fragmented-baseline "$PWD"

# Deterministic operation-count and preservation tests, without timing assertions.
bun test packages/word/test/paragraph-occurrences.test.ts
```

Baseline: `4d1465ddf85ee238a727dbed75aac7bf043f05f8`. Hardware: Intel Celeron
N5095 at 2.00 GHz, four logical CPUs, Linux x86-64. Runtime: Bun 1.4.4. Fixtures
are generated by the benchmark and contain no user documents.

An initial unlocked run experienced substantial shared-host contention, with
load near 20 on four cores. Those timings are excluded from speedup comparisons.
The reported rerun holds the shared advisory lock across both revisions and all
sizes, with no concurrent tests from this thread. The lock coordinates audit
threads; it does not reserve the machine against unrelated processes.

## Results

All values below come from the single locked before/after sequence. Times are
medians of three measured samples after one warmup. [Raw samples](word-fragmented-export-benchmark.json)
include the excluded contended baseline as well as every locked sample.

| Runs | Before wall, ms | After wall, ms | Before CPU, ms | After CPU, ms | Wall ratio |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 8,000 | 1,366.4 | 417.2 | 1,619.0 | 648.7 | 3.28x |
| 16,000 | 8,494.3 | 757.9 | 8,664.1 | 1,126.3 | 11.21x |
| 32,000 | 35,090.7 | 1,426.7 | 35,732.9 | 2,118.1 | 24.60x |

Doubling size increased baseline wall time by 6.22x and 4.13x, versus 1.82x and
1.88x after the change. At 32k, process CPU time fell by 16.87x. CPU time sums all
process threads, so it can exceed wall time. These are fixture-specific results
on a shared host, not a latency guarantee.

| Runs | Before peak RSS, MiB | After peak RSS, MiB | Before median heap delta, MiB | After median heap delta, MiB |
| ---: | ---: | ---: | ---: | ---: |
| 8,000 | 182.6 | 194.8 | 30.9 | 39.1 |
| 16,000 | 291.6 | 286.6 | 85.1 | 84.2 |
| 32,000 | 489.5 | 535.5 | 49.9 | 136.9 |

There is no measured memory improvement. At 32k, peak process RSS increased by
46.0 MiB, about 9.4%. Net heap changes depend on garbage collection and must not
be interpreted as total allocations. The remaining-occurrence map has one entry
for this fixture instead of one per source run, but this does not establish a
reduction in total export memory.

## Work counts and preservation

The focused test instruments original-run `source` reads during rendering,
after renderer setup. With 256 runs, reads fell from 33,919 to 256. Adding 256
empty continuations increased the baseline to 164,991 reads; the fixed version
still made 256. The assertions permit at most four reads per original run and
contain no timing threshold. Exact after counts were captured by logging the
existing `reads` variable in a temporary copy of the two operation-count tests.

On the audit baseline, both work-count guards fail and all ten preservation cases
pass. With the fix, all twelve pass. They cover duplicate sources, paragraph
splits and joins, deleted runs, reordering, tabs and breaks, paragraph and run copy
scopes, header page fields, and opaque bookmark boundaries in Strict and
Transitional documents. Existing package tests additionally cover copied tables
and rows.

For each benchmark size, all six measured outputs across the two revisions have
identical XML byte counts and SHA-256 hashes. The benchmark also verifies the
reimported run count and each run's text after every warmup and measured export.
This is equivalence evidence for these fixtures, not external Word/LibreOffice
qualification.

Local validation, run sequentially after benchmarking under the same lock:

- `bun test packages/word/test/paragraph-occurrences.test.ts`: 12 pass, 0 fail.
- `bun run check`: pass.
- `bun test`: 1,439 pass, 0 fail across 172 files.

The execution payload had a ten-minute timeout after acquiring the lock. No
local docs build or browser suite was run for this headless change; PR CI owns
those checks.
